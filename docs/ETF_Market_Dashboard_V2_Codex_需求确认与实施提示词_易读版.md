# 第一部分｜给使用者看的改造目标与好处（建议先确认）

## 1. 为什么需要这一轮升级？

目前的 ETF 看板已经有红利/成长比较、三棱镜轮动、五年之锚、股息监测、ETF 资金流向等研究功能。现在最需要解决的，不是再增加几张图，而是回答五个实际使用问题：

1. **我打开图表，能不能相信数据？** 数据是否更新成功？来自东方财富还是新浪？是否与上次口径一致？
2. **我发现一张图异常，能不能快速知道原因？** 是数据源故障、缺失交易日、分红折算、校验失败，还是程序错误？
3. **我在本地改好代码上传服务器，会不会把服务器上新更新的数据覆盖？** Windows 与 Linux 是否始终读取相同的发布版本？
4. **我让 Codex 修改前端，怎么确认其他图表没有被改坏？** 不依赖每次逐页手工点开检查。
5. **我做历史回测时，结果能不能复核？** 能否明确输入数据、公式、成本、交易时间，以及当时使用的快照版本？

**本轮升级的最终效果**：日常使用时“看得见数据状态、查得到问题原因”；开发更新时“只部署代码、不破坏数据”；研究分析时“数据可追溯、计算可复核”；改动代码时“自动测试先把明显错误拦下来”。

## 2. 11 项改造：现在不方便在哪里，改完能得到什么？

| 编号 | 改造主题 | 目前的实际困扰 | 改完对你的直接好处 | 怎么判断做对了 |
|---|---|---|---|---|
| 01 | **统一数据获取入口** | ETF、指数、股息、份额等各用各的采集函数，新增来源和排查问题时逻辑分散 | 日后增加或替换数据源，只需接入统一适配器；数据源状态有一致的描述方式 | 用同一套接口获取多类数据，能看到具体调用了哪个上游、失败在哪里 |
| 02 | **防止错误的数据源切换** | 主源失败后备用源可能直接覆盖已有历史行情 | 即使上游故障，历史收益曲线也不会因口径不同而悄悄变化 | 模拟主源故障、备用源数据不同：旧版数据继续可看，异常被拦截并展示 |
| 03 | **数据来源可追溯** | 图上一个异常点位不一定能追到当时的原始记录 | 能回答“这个数从哪来、何时抓的、为什么采用它” | 从图表数据集可以查到发布版本、采用的规范化记录和真实原始证据；查不到就明确标记未知 |
| 04 | **一个汇总式数据中心** | 想知道哪些数据更新成功，要到不同页面或日志里逐个排查 | 打开一个页面，就能看到全部数据集是否正常、最新日期、异常原因及受影响看板 | 数据中心正确区分采集成功、校验成功、发布成功；异常可定位到标的和日期 |
| 05 | **防止数据库与图表使用不同版本** | 更新过程中出错，可能出现 SQLite 已变、JSON 快照没变 | 页面永远读取一套完整且一致的数据，不看到“更新一半”的结果 | 强行中断发布后，图表仍显示上一完整版本；恢复后可重新发布 |
| 06 | **UI 自动化测试** | 每次改 JS/CSS 都需要手工打开多张图检查 | Codex 修改后自动检查核心图表、交互与手机布局，减少回归故障 | 一条命令跑 Playwright，能提供通过/失败记录与固定测试截图 |
| 07 | **数据与代码分开存、Git 不跟踪运行数据** | 项目压缩包被历史快照、备份撑大；Git 可能跟踪运行数据 | 上传更快、仓库更干净，也避免把真实数据库当代码更新 | 部署包不含数据库、快照、密钥；服务器的数据目录独立存在 |
| 08 | **本地开发与服务器部署有明确规则** | Windows 开发、Linux 运行，数据源和路径差异可能造成不同结果 | 代码可频繁更新，但服务器的主数据库、快照不会被本地旧版本覆盖 | 模拟部署一次新代码后，服务器测试数据及版本保持不变；失败可回退 |
| 09 | **统一金融计算口径和回测记账** | 有些策略的收益、费用和交易时间不易横向比较 | 研究结果更可比，避免因为公式或成本处理不同产生假优势 | 使用人工可算的小样本，自动验证收益差、初始建仓、换仓费用和执行时点 |
| 10 | **前端代码边界更清晰** | 部分脚本过于集中，修改一处可能影响其他页面 | 后续改图表更安全，也更容易由 Codex 定位模块 | 图表、数据 API、状态逻辑可以独立测试，既有页面不退化 |
| 11 | **统一更新任务与运行记录** | 更新失败原因、执行耗时、重复执行等不易集中查看 | 能一眼看到今天更新了什么、耗时多久、卡在哪一步，必要时安全重试 | 同一任务不会重复执行或覆盖，日志与数据中心能对应到同一个任务编号 |

**优先次序**：先保证“程序运行和金融数据正确”，再完善“数据中心”，然后解决“部署和维护”，最后做“UI 规范化”。测试不是最后才做，而是**每完成一个阶段就同步补测试**。

## 3. 对使用体验影响最大的三项（重点确认）

### A. 数据中心——从“看日志查错误”改为“一个页面查全部数据”

**现在的困扰**：今天轮动图没有更新，你可能不知道是 ETF 价格没抓到、指数更新失败，还是更新已经完成但没有发布。

**改造目的**：让系统像一个有运行状态面板的仪表台。建议左侧导航新增**独立一级页面「数据中心」**，绝不在每张轮动图下面复制一套管理表格。

**你将看到：**

- **总览**：共有多少数据集，多少正常、陈旧、异常、来源未知；最近一次采集与最新有效发布分别是什么时间。
- **数据集清单**：ETF 行情、指数行情、ETF 份额、股票/ETF 股息、债券/估值等；每项显示最近有效交易日、主源与真实上游、更新结果和数据质量。
- **异常详情**：例如“510330 的某个历史交易日与主源差异超出规则，新数据被隔离”，可以查看差异和来源而非只看到红色错误提示。
- **更新记录**：谁/什么任务触发、开始结束时间、抓取是否成功、校验是否通过、是否真正发布。
- **受影响看板**：同一指数异常时，列出三棱镜、五年之锚等哪些页面使用它；已存在的旧数据仍然有效时显示“沿用上一版”。

**业务看板仍然以图表为主**，标题附近只显示“数据截至某交易日 / 正常或陈旧 / 查看数据中心”，不挤占绘图区域。

**为什么值得做**：这项工作可以显著降低每次数据更新后的人工排查成本，并让你判断策略变化时先区分“真实市场变化”还是“数据变化”。

**验收情景**：当天数据采集成功，但校验失败。数据中心必须显示“采集成功、校验失败、未发布”；原业务页面继续读取上一完整版本，并标记数据陈旧，绝不能同时显示“今日已成功更新”。

### B. 主源锁定 + 数据质量门禁——避免同一策略因上游切换而改变历史结果

**现在的困扰**：你以前就遇到 Windows 本地正确、Linux 服务器行情不同的情况；主源临时失败时切到了别的上游。

**改造目的**：把“请求到了数据”和“这批数据允许用于投资分析”分开判断。统一 Provider 负责采集；独立质量门禁负责判断是否可以采用。

**你将得到的好处**：主源短期故障不再导致历史价格、相对收益差和回测结果悄悄变化；发生差异时能查清是哪一个数据提供方、哪一段日期、哪一种收益口径造成的。

**验收情景**：模拟东方财富失败，新浪返回一份价格不同的历史数据。系统可以记录并保存候选数据以便对账，但不能直接替换可信历史或发布给图表。若数据一致且符合既定来源策略，才允许采纳。`PASS` 仅表示相应内部检查通过，不得被解释成已完成外部事实核验。

### C. 代码与数据分离部署——以后更新代码不再重复搬运历史数据库

**现在的困扰**：本地压缩上传时，把已有数据库、原始数据、快照和备份一起打包，体积大，且容易与服务器上更新后的数据冲突。

**改造目的**：让服务器的数据目录独立持久化。日常部署只发送 Python、JS、CSS、HTML 和必要的静态资源；服务器自己的 SQLite、已发布快照、原始证据和备份不随代码包替换。

**你将得到的好处**：上传速度和回滚效率明显改善；本地改动一个页面也不需要重新复制历史行情；服务器能定时更新数据；升级失败可恢复旧代码而无需回滚数据。

**推荐默认方案**：**服务器维护权威运行数据，本地负责代码开发和测试**。如果 Wind MCP 或 ETFirst 的某些数据确实必须在本地采集，单独提供“本地数据发布包”，先校验版本与哈希再导入服务器，不能直接复制在线 `.db` 和零散 JSON 覆盖。

**验收情景**：先在测试服务器准备一份比本地更新的数据版本，然后部署新代码。部署成功后，数据仍是服务器原来的较新版本；模拟部署失败，代码回退但数据库与快照不损坏。

## 4. 完成后，你每天的典型使用流程

**交易日数据更新后**：打开数据中心，看“哪些数据集完成采集/校验/发布”，异常项能展开具体原因；若没问题，进入轮动和股息看板进行研究。

**某条曲线突然大幅变化时**：先点击该图旁的“数据详情”，核对截至日期、数据上游、是否有分红/拆分调整和历史修订；数据异常不再需要翻 Python 日志猜测。

**Codex 改完代码后**：先跑 Python 测试、关键 API 检查和 Playwright 浏览器测试。测试报告说清楚通过什么、没通过什么，不能只写“功能正常”。

**准备上传服务器时**：生成不含 `data/` 的代码包；服务器更新代码后做健康检查。数据库与快照保留在独立目录。备份和历史快照定期归档，但不允许自动删除没有确认过的金融原始证据。

# Codex 执行任务：ETF Market Dashboard V2 工程架构、数据可靠性与自动化质量保障专项升级

## 0. 角色、任务和成功定义

**给项目使用者的解释**：这次不是把代码变“高级”，而是减少日常数据更新、服务器同步、回测复核和后续改版时的意外成本。只要系统能用稳定且可验证的方式完成原有任务，就不要求更复杂的技术栈。


你现在担任本项目的**技术负责人、金融数据工程师、Python/FastAPI 工程师、前端质量工程师和测试负责人**。请直接在当前已检出的 `etf-market-dashboard` 仓库工作。你的交付物不是建议书，而是**实际代码修改、必要的数据迁移/部署脚本、自动化测试、可复现的验收证据和完整文档**。

项目定位：单用户个人 ETF/股票研究看板；Windows 本地开发，Linux 服务器运行；主要技术栈 FastAPI + SQLite + HTML/CSS/原生 JavaScript + ECharts。现有业务包含红利/成长 ETF 比较、三棱镜轮动、沪深300 ETF 资金流向、ETF/股票股息率、五年之锚、A/H 红利研究和股债性价比。

**成功的定义：** 在不破坏现有功能及历史数据的前提下，实现统一数据源接口与策略、来源可追溯、严格的数据发布门禁、跨平台和跨介质一致性、统一集中式数据中心、安全的本地→服务器部署、可靠的任务运行记录，以及可在离线环境执行的自动化测试体系。每项必须有明确可复现的“通过/不通过”证据。

这是“更深的版本，而不是更大的版本”。不要添加投资策略、AI 选股/建议、多用户、注册登录、微服务、Kubernetes、消息队列或全量 React/ORM 迁移。优先最小兼容改造。

## 1. 不可违反的约束

1. 保护历史 SQLite、`data/raw/`、`data/releases/`、`data/backups/`、`data/current_manifest.json`、研究数据和本地未提交修改；先识别后备份，**禁止未经授权删除、覆盖或重写真实历史金融数据**。测试必须用临时数据库、临时目录及固定 fixture。
2. 先检查 `git status`、实际目录、现有测试和运行方式。此前审阅仅是调查线索，不是对当前代码的事实保证；已修复问题应验证通过并记录，而非重复修改。
3. 不改变已有业务页面/导航的主要功能；不破坏现有 API 消费方，新增字段以向后兼容方式扩展；需要破坏性变更时实现兼容层和迁移测试。
4. 保留主图的**单图复合展示**：红利、成长、沪深300基准、50:50 累计收益曲线以及“红利减成长收益差”柱状图必须叠加在同一张图上，不得拆成上下两图。
5. 数据中心是**全局集中式一级页面**，不在每个轮动看板下复制一套数据管理模块；业务看板只保留精简的截止日期/质量状态/跳转链接。
6. 禁止把“请求成功”“结构校验 PASS”“有来源字段”直接等同于“外部事实核验”；未知必须显示 UNKNOWN，不能伪造原始证据或验证结果。
7. 禁止以“备用源返回非空”作为发布许可；不同来源必须先检查证券标识、市场、复权/全收益定义、币种、单位、交易日和历史重叠区间。
8. 不依赖真实 Wind/ETFirst/行情网络服务才能完成离线 CI；真实在线抽查应另行报告，离线测试通过不能宣称已验证实际行情正确。
9. 公开访问的服务器不引入账号体系，但任何有修改能力的管理接口不能无保护地暴露；优先复用现有部署的反向代理/访问控制或绑定 localhost，避免在日志和诊断 API 暴露 token、cookie 和密钥。
10. 不做无目的“全面重构”。每次修改说明动机、影响模块、兼容性和回滚方式。若当前工作树包含用户未提交改动，必须保留，不能 `git reset --hard` 或清理未识别文件。

## 2. 第 0 阶段：先建立真实基线与影响清单

**为什么先做这一阶段**：如果不先确认哪些问题仍存在，Codex 可能把已修复功能再次改坏，也无法证明升级真的改善了什么。**你能得到的结果**：一张“当前哪里有问题、哪些已经正常、哪些依赖网络无法测试”的清单，作为升级前后的对比依据。


开始修改前：

- 输出**模块—数据集—数据源—规范化存储—发布快照—API—前端页面**对应关系，标出跨模块共享的输入依赖；特别列出每条数据的单位、复权/总收益口径和实际最上游来源。

- 在 `docs/engineering-v2/00-baseline.md` 保存实际证据、问题定位和改造计划；后续文档用此基准对比。

## 3. 第一优先级：跨平台读取、健康检查、发布一致性（P0）

**为什么做**：解决“本地正常、服务器打不开”和“更新到一半导致图表数据错乱”。**直接好处**：即使出现网络、进程或磁盘故障，至少能稳妥使用上一版完整数据，并且健康检查不会报告假正常。**业务验收**：模拟发布中断或错误路径，图表继续读取同一套有效旧版本，页面能明确说明出了什么问题。


### 3.1 统一快照路径与读取

- 新 Manifest 统一用 POSIX 相对路径，旧清单读取时兼容 `\\` 与 `/`；使用 `pathlib`/安全路径解析，拒绝绝对路径、盘符注入、`..` 越界、软链接越界等。不得在用户输入中直接拼接文件系统路径。
- 由统一的 Snapshot Repository/Reader 服务读取并验证 Manifest，而不是 `server.py`、五年之锚、红利研究各自解析。检查**存在性、SHA-256、JSON schemaVersion、snapshot_id、必要数据字段及发布状态**。已发布 release 文件不可被原地编辑。
- 当前 `/api/snapshot`、`/api/snapshot/data/...`、`/api/rotation/overview` 以及其他依赖快照的接口应在 Windows/Linux 读取同一版本，且不会因缓存返回与 Manifest 不符的内容。
- `/api/health` 保持兼容，新增/扩展 readiness 与数据质量状态：进程活着、核心数据可读、数据新鲜是不同概念；关键文件坏了不得报告全正常。

### 3.2 可恢复的 SQLite + JSON 发布协议

- 不声称 SQLite 和文件系统可直接做到跨介质 ACID；实施应用层 `STAGED/PREPARED/VERIFIED/PUBLISHED/FAILED` 等等价状态机。
- 先写 staging、检查数据和哈希、生成完整 Manifest、确保数据库与待发布快照绑定同一 `release_id`，最后原子切换发布指针；客户端永远只读完整且验证通过的发布版本。失败保留上一版，进程重启后可清理/恢复不完整发布。
- 为失败点注入测试：写库前、写库后、生成文件中、Manifest 切换前后；多进程/重复发布幂等；高并发读取不得看到混合版本。严格区分“SQLite 更新成功”与“对外发布成功”。

## 4. 第二优先级：统一 Provider + 来源策略 + 数据质量门禁（P1）

**为什么做**：采集入口分散导致查错成本高，自动切换上游又可能影响历史价格可比性。**直接好处**：新加数据源更省事；异常源不会不经检查就覆盖原来可靠的行情；来源差异有记录可追。**业务验收**：故意让主源失败并让备用源返回不同口径的数据，系统能保存候选并告警，但原图表历史曲线不发生静默改变。


### 4.1 Provider 抽象只管“获取”，不直接决定“发布”

基于已有 `FetchResult`、原始数据/规范化数据能力进行增量改造，不机械重写全部采集器。

- 定义最小 `DataProvider`/Adapter 契约：支持范围（标的类型、市场、数据集）、`fetch(request) -> FetchResult`、超时/重试/错误分类、来源信息、采集时间、行数；能适配 AkShare（明确东方财富/新浪等真实 upstream）、ETFirst、Wind MCP 及已有其他来源。
- 定义标准请求：`instrument_id`（交易所/市场+代码、指数与 ETF 区分）、`dataset_type`、`date_range`、`adjustment`、`return_type`、`currency`、`unit`、`calendar`、`as_of`。
- 构建 Provider Registry/Capability Matrix 和 DataProviderManager：统一可用性、流控、超时、有限重试、短期熔断、采集日志、候选源选择。所有策略均通过标准化后的数据访问层读取，不让策略代码直接按供应商字段猜测口径。
- 配置 `SourcePolicy`，按**数据集 + 标的/市场 + 经济含义**明确主源、候选源、何种条件可切换、哪些字段只可核验不可自动替代。配置需可审计，不允许静默改变主源。

### 4.2 独立 Quality Gate

- 原始数据先写入不可变的 Raw Observation（尽可能保留上游原始响应；如果仅保存中间 DataFrame 序列化，要如实标注为“接收后结构化原始快照”，不得误称 HTTP 原始响应）。
- 验证：schema、代码/交易所、时区与交易日历、字段范围、缺失与重复、价格跳变、历史重叠差异、复权/分红/基金份额折算、单位/币种及指数全收益含义；差异阈值按数据类型配置，不只设置 20% 涨跌幅阈值。
- 备用源数据不一致时进入 Quarantine/Candidate 区，记录 `quality_issue`、差异明细、涉及日期及上游证据；阻止规范化覆盖与发布，保留上一个可信版本。
- Quality Gate 输出**计算可用性、数据新鲜度、来源可信度、历史完整性**四个独立维度。外部核验字段不得从内部 `PASS` 推导。允许合法缺失时标记 `PARTIAL` 而非伪造零值。
- 完成 Raw → Canonical → Release → API 的溯源链接。新采集的 canonical 必须关联实际选用 raw ID、采集批次、源/上游、时间、摘要和核验状态；历史无法重建证据的数据标记 UNKNOWN，不得伪补。

### 4.3 最低试点范围和扩展

首先用 `510330`、`512530`、`562310` 的同口径 ETF 收盘价进行完整试点，覆盖 Windows/Linux 和主源/备用源冲突。通过后迁移指数、ETF 份额、分红、股债等已有数据集。优先调用现有脚本的 Adapter 包装层，尽量不改变业务模块输出格式。

## 5. 第三优先级：集中式数据中心与任务可观测性（P1）

**为什么做**：现在需要分散查日志才能知道数据更新结果，而且“抓到了”不代表“验证了”，更不代表“已经显示到图上”。**直接好处**：一个汇总页面就能看到数据状态、异常、发布版本以及受影响的业务图表；减少每日人工核查。**业务验收**：采集成功但校验失败时，数据中心准确写出“三阶段不同状态”，页面不误报成功。


### 5.1 统一数据中心（独立一级导航）

新建一个**汇总型数据中心**，按底层**数据集**组织，而不是每个轮动策略复制一套面板。第一版以只读诊断为主，后续可安全接入手动重试。

至少包含：

1. 总览：总数据集、成功/部分/异常/未知/陈旧数量、最近一次采集完成时间、最近有效发布版本、发布是否成功、数据库/快照空间占用。
2. 数据集清单：数据集名称、覆盖标的与日期、最新有效交易日、预期交易日、主源/实际 upstream、上次成功与失败、抓取行数、缺失/重复/冲突数量、采集状态、校验状态、发布状态，支持按状态筛选。
3. 运行任务：`job_id/trace_id`、触发方式、开始/结束、耗时、阶段（采集/候选对账/规范化/发布）、成功/失败/部分成功、简要错误、可查看脱敏诊断。
4. 异常与溯源：可下钻到具体标的与交易日期、原始 ID、标准化记录 ID、来源、对账差异、原因及是否阻断发布。
5. 策略依赖影响：基于真实调用关系建立 `dataset -> affected_dashboard` 映射，展示哪些页面仍在用旧版、哪些数据已失效，不把“今天更新失败”误写成“历史策略不可用”。
6. 版本与存储：当前/前两版可恢复 Snapshot、历史归档及备份元信息；只读浏览为主，危险的回滚/清理不在第一版提供无确认按钮。

状态至少区分 `UNKNOWN/NOT_CONFIGURED/RUNNING/FETCH_FAILED/FETCH_OK/VALIDATION_FAILED/PARTIAL/VERIFIED/PUBLISHED/STALE` 的适当等价集合，**采集、验证、发布分别展示，不能只用一个成功字段**。状态定义、数据新鲜度阈值和市场交易日历必须在后端统一，不由各页面自行推断。前端只读取一个或少数几个有稳定 schema 的 Data Center API；错误、空态、部分可用、重试与权限/敏感信息脱敏均需覆盖。

### 5.2 各业务页面只保留轻量状态

保持业务图表布局不变，仅添加简短的“截至交易日 / 使用版本 / 数据质量状态 / 查看数据中心详情”入口，点击直接定位对应数据集。不要在每个看板下方新增完整 Provider 表或维护组件。

### 5.3 更新任务

- 将慢速全量数据刷新与 HTTP 请求响应生命周期解耦，创建持久化 job 状态；如现有异步任务已可用则复用，不必引入 Celery/Redis。
- 对同一数据集、同一逻辑更新窗口实现幂等去重与**跨进程**互斥；手工触发与定时触发不能造成互相覆盖；记录任务阶段和可诊断失败，不把任务排队或单个数据集成功显示为“全部发布完成”。
- 优先使用现有单机调度机制或 systemd timer/cron；仅需本地单机运行，避免分布式调度架构。采集工作默认以服务器为权威数据运行端。

## 6. 第四优先级：本地/服务器部署、持久化、Git 管理（P1）

**为什么做**：代码和行情数据一起上传，既慢又有覆盖风险。**直接好处**：改一个前端文件不再需要传一大包历史数据，服务器可长期保留自己的主数据库；代码升级失败可以独立回滚。**业务验收**：先让服务器拥有较新的测试数据，再部署本地新代码，数据版本仍保持原样。


### 6.1 代码/数据物理隔离

保留原生 FastAPI + SQLite：默认支持 `ETF_DATA_DIR` 独立持久化数据目录，兼容旧项目的 `data/` 路径和 Linux 软链接。不要把主 SQLite、Raw、已发布快照、历史备份、密钥或日志纳入每次代码部署。

支持两种清楚界定的数据更新方式：

- **A（默认）：服务器维护权威数据。** Windows 本地只开发/测试并上传代码；服务器在独立数据目录增量采集与发布。部署代码绝不以本地旧数据覆盖服务器数据库。
- **B（可选）：本地采集后同步数据包。** 只允许通过包含 SQLite 一致性备份、候选快照、Manifest、哈希、schema/release_id 的发布包上传并校验后切换；不能直接覆盖在线数据库和不同版本 JSON。

### 6.2 安全部署与回滚

- 提供 Windows PowerShell 打包/上传示例与 Linux 安全安装/升级脚本（按当前实际部署方式实现），可按版本生成代码 release，失败回滚代码；服务器数据版本独立管理。
- 脚本默认 dry-run 或强校验；检查路径、磁盘空间、必要环境变量、数据库兼容性、旧版备份、服务进程状态；升级后执行健康/就绪检查。不可在不确定部署根目录或数据位置时自动移动/删除。
- 修复 Windows Manifest 在 Linux 不可读、相对路径和工作目录依赖；部署必须兼容实际运行用户权限和不同盘符/路径分隔符。

### 6.3 Git 与历史数据

- 盘点 Git 已跟踪的运行数据；完善 `.gitignore`，并采用安全、可审计的**仅从 Git 索引解除跟踪**流程；必要的种子数据/测试 fixture 留在仓库。绝不删除实际 `data/` 或在未审查 Git 历史情况下执行激进历史改写。
- 按当前发布、最近两版可回滚快照、长期归档、SQLite 周期性备份分类管理；对 `releases/` 与 `backups/` 仅提供空间分析、引用关系检查和清理预览。未经用户批准不执行历史数据删除。
- SQLite 在线备份使用官方 SQLite Backup API 或经证明一致的方法；包含完整性验证、备份恢复测试、WAL 情况处理；不能直接把正在写入的 `.db` 单文件复制当作可靠备份。

## 7. 第五优先级：策略正确性、前端模块化、UI 自动化（P1/P2）

**为什么做**：策略公式、成本口径如果不一致，回测排名就可能有偏差；前端靠手工点查又容易漏掉回归问题。**直接好处**：关键指标可手算复核，未来改动一个看板时能自动检测其他页面是否被改坏。**业务验收**：固定的小样本手算结果完全一致，桌面和手机测试能重复运行并保留截图。


### 7.1 金融计算与交易时序

核对红利/成长、三棱镜、五年之锚、红利 A/H 回测、股息率、ETF 份额与资金流、股债性价比的计算定义和输入口径。要求：

- 区分 ETF **未复权价格收益、复权收益、含分红再投资总收益**和指数价格/全收益指数；不可将缺失分红按零分红处理。
- 明确 50:50 是初始等权买入持有还是定期再平衡；保留当前既有主图含义并准确标注。
- 三棱镜 40 日收益差、比值、布林线、RSI 的公式、预热、缺失、交易日和参数应由唯一计算实现定义，不能前后端两套公式暗中分叉。
- 回测所有策略与对照基准统一初始现金、初始建仓、持仓漂移、再平衡、换手、单边交易成本、交易时点和未来函数约束；先修复已指出的 A/H 基准初始建仓成本差异。
- ETF 净申购量估计需要考虑份额折算/拆分、份额单位与 NAV；不能将份额变化直接归因于特定投资者（如“国家队”）。
- 选取可人工手算、无外部行情依赖的黄金样本进行逐步验证。对外金融事实还需可定位的交易所、指数公司、基金公告或数据商来源；“测试通过”与“行情事实已核验”严格区分。

### 7.2 前端可维护性

保留原生 JS + ECharts，适度抽出 `api-client / state / charts / page-modules / quality-indicator` 等边界。消除影响正确性的重复函数覆盖、异步竞态和图表实例泄漏；不进行 React/Vue 全量改造。

### 7.3 自动化 UI 测试体系

采用 Playwright（或现有适合工具）建立稳定 E2E fixture：不依赖真实上游网络、不需要 API key，在本地固定数据库/模拟 API 下运行。覆盖主看板单图复合曲线、三棱镜、轮动总览、资金流、股息、五年之锚、股债及**集中式数据中心**。至少测试 1440px 桌面与 390px 移动端，必要时增加 768px；验证主要标题、图例、数值、日期切换、异常/空态、状态跳转、加载和重试、浏览器 Console 无未处理错误，以及全局横向溢出。表格允许局部滚动但需提示。

截图回归要求固定浏览器、字体、时区、测试数据和动画/时间轴，不能在不同 OS 上直接对比像素基线；有合理差异时解释并审查图片，不得盲目更新所有金图。ECharts 需确保动画完成后截图。

## 8. 必须自动化验收的测试矩阵

**为什么这些测试重要**：单纯运行一次“没有报错”无法证明历史数据没被覆盖、发布中途出错不会破坏旧版、手工操作没有遗漏其他页面。这里的测试专门模拟真实使用中最容易出问题的场景。**你看报告时只需要关注**：哪个情景实际通过、哪个失败、哪个因为缺少环境没跑；每一项都要能定位到命令和证据。


在 `tests/` 和前端测试目录中增加以下离线、可重复、可独立运行的测试，并给每项测试唯一 ID：

| ID | 测试输入/故障注入 | 必须满足的判定 |
|---|---|---|
| T01 | Windows `\\`、POSIX `/`、混合路径 Manifest | Windows/Linux 均读取相同合法发布数据 |
| T02 | `..`、绝对路径、盘符及软链接越界 | 访问被拒绝，绝不读出数据根目录外文件 |
| T03 | 删除/篡改 Snapshot、SHA 错误、`snapshot_id` 不匹配 | API/数据中心明确报错；不能显示为有效发布 |
| T04 | 主源超时/限流，备用源可用但口径不明 | 只产生候选，现有 Canonical 与发布快照保持不变 |
| T05 | 主/备源同口径重叠区间一致与不一致 | 一致按策略通过；冲突阻断发布并产生可追踪差异 |
| T06 | Raw 记录缺失或 provenance unknown | 不伪造证据，Canonical 核验状态仍是 UNKNOWN |
| T07 | 数据库已提交但 Snapshot 未切换时进程崩溃 | 读端仍只见上一完整版本，重启可恢复/重试 |
| T08 | 重复触发与并发更新同一数据集 | 不产生重复发布、相互覆盖或不一致状态 |
| T09 | 休市、跨市场交易日、时区与陈旧数据 | 不把休市误判为更新失败；标出真实有效交易日 |
| T10 | 原始分红、缺少分红、份额折算/合并 | 数据口径和异常标识正确，不凭空填 0 |
| T11 | 红利 +10%、成长 -10% 的固定序列 | 累计收益差 +20 个百分点，初始 50:50 不再平衡组合净收益 0%（不计成本），主图单图展示 |
| T12 | 初始建仓/全仓切换/持仓不变/部分调仓 | 回测与基准采用同一可手算的换手、费用和净值规则 |
| T13 | 更新抓取成功但验证失败、验证成功但发布失败 | 数据中心分别显示各阶段状态，无假阳性“成功” |
| T14 | 某数据集陈旧但仍有上一有效版本 | 关联看板显示“沿用旧版/数据陈旧”，不是空白或伪正常 |
| T15 | Data Center 冷启动、空集、部分可用、API 出错 | 状态正确、可重试，其他数据集正常显示，密钥不泄露 |
| T16 | Windows 打包 → Linux 部署（使用临时路径/测试环境） | 程序可读取数据，部署不会覆盖服务器独立数据目录 |
| T17 | SQLite 备份→恢复、历史快照清理 dry-run | 完整性与引用检查成功，未确认前没有删除操作 |
| T18 | 主要页面桌面/手机浏览器 fixture | 主图保留单图复合，控件可用、无未处理异常或全局横向溢出 |

不得“只增加测试文件而不执行”。对不具备 Windows/Linux 双系统的当前 Codex 运行环境，可增设 GitHub Actions Windows+Ubuntu 测试矩阵，并在本地验证其余测试；实际未运行的平台必须标注**待对应环境执行**，不能伪称跨平台已实测。真实供应商连通性测试单独标记 integration/live，默认 CI 不调用外部网络。

## 9. 各阶段客观完成门槛（Definition of Done）

**为什么做**：防止 Codex 把“写完代码”当成“解决问题”。每个阶段都要有可以复核的测试记录，不允许用“预计有效”“理论支持”或截图代替验证。


- **基线门**：完整测试统计、当前工作树与依赖清单、模块依赖关系已记录；对审阅问题逐条验证“存在/已修复/环境受限”。
- **跨平台门**：T01–T03 全通过；所有快照核心 API 一致读取并验证哈希；关键快照损坏时 readiness 不显示正常。
- **数据可信门**：T04–T06、T09–T10 全通过；新 Canonical 的来源关联可回溯；未经核验的备用源不能进入已发布版本。
- **发布门**：T07–T08 全通过；故障注入后能恢复最新完整发布；所有下游接口可定位到实际 `release_id`。
- **数据中心门**：T13–T15 全通过；清单、状态、诊断、异常、依赖影响和版本信息能从服务端事实取得，不靠前端编造。
- **部署门**：T16–T17 在已执行的平台通过；源代码发布不触碰服务器持久化数据；备份可恢复；清理默认仅预览。
- **金融计算门**：T11–T12 及所有核心策略原有测试通过；对于没有可靠外部数据的全收益/股息功能不得冒充验证通过。
- **UI 门**：T18 通过；固定数据的 ECharts、交互与关键页面回归可复现；截图和测试结果存档。
- **总体门**：现有完整测试没有由本次改动引入的新失败；已确认缺陷优先修复。环境缺失、历史测试契约变更、生产依赖不可达必须分别列明，不得通过删测、无依据调整断言或大面积 skip 粉饰结果。

验收报告对每个项目列 `PASS/FAIL/BLOCKED/NOT_RUN`，附：测试命令、退出码、日志路径、Git SHA、运行平台、实际输出、是否依赖模拟数据。不能把 `BLOCKED` 或 `NOT_RUN` 当 `PASS`。如不能访问官方数据，金融事实应标为“未完成独立外部核验”。

## 10. 成熟项目与标准参考（借鉴方法，不直接复制架构）

**借鉴原则**：成熟项目提供已经有人实践过的设计方法，但它们的目标未必与你相同。参考它们的数据源接口、诊断页面、自动化测试和安全备份，保留你现有的历史数据质量门禁与版本化快照。不要求迁移到 React、全量 ORM 或 Docker。


1. **ZhuLinsen/daily_stock_analysis**：https://github.com/ZhuLinsen/daily_stock_analysis
   - `data_provider/base.py`：BaseFetcher、DataFetcherManager、能力与熔断；只借鉴接口、可观测性，**不得直接复制自动切源即采纳的语义**。
   - `src/services/data_capability_service.py` + `api/v1/endpoints/data.py`：统一数据能力与质量只读契约。
   - `apps/dsa-web/src/pages/DataCenterPage.tsx` + `docs/data-center-diagnostics.md`：集中式 Data Center 的状态、空态、异常展示。
   - `src/services/run_diagnostics.py`：trace_id、provider、latency、fallback、失败详情的诊断字段。
   - `src/services/scheduled_analysis_claim.py`：SQLite 计划任务原子认领，防重复运行。
   - `.github/workflows/ci.yml`：前端 lint/build/浏览器 fixture 测试与证据上传。
   - `src/core/etf_rotation.py`：纯计算策略、信号/执行时间及统一交易成本思想；**不能直接替代当前三棱镜策略定义**。
2. **Playwright 官方视觉回归说明**：https://playwright.dev/docs/test-snapshots —— 固定测试环境和金图比较，避免跨 OS 像素误判。
3. **pytest 官方 fixture 文档**：https://docs.pytest.org/en/stable/how-to/fixtures.html —— 临时数据库、供应商模拟、故障注入与隔离验证。
4. **Python sqlite3 Backup API**：https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup —— 在线一致性备份与恢复验收。

应遵守引用项目的许可证，不批量复制不必要代码；如复制具体片段，记录来源和许可。任何参考实现都不能替代本工程自己的回归测试和金融数据口径证明。
